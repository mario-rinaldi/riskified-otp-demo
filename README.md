# Riskified OTP demo — pre-auth sync decide, Review original flow

A local harness for demoing the OTP recovery flow end to end: a stand-in merchant
checkout on the left, a live console on the right showing every request, header,
signature and decision as it happens.

## Why there's a server

The page can't call Riskified directly. Requests are authenticated with an
HMAC-SHA256 signature computed over the raw request body using the shop auth
token, so putting the token in client-side JavaScript would expose it, and the
API doesn't serve CORS headers to a page origin. The Express server signs and
forwards; the browser only talks to `localhost`.

## Setup

```bash
npm install
cp .env.example .env
npm start
```

Open http://localhost:3000. The sandbox credentials are already in
`.env.example`, so this runs as-is.

To rehearse with no network at all:

```bash
SIMULATE=true npm start
```

## The Beacon

The Beacon is a Riskified script that collects device and behavioural signals in
the browser. Those signals are only useful if they can be matched to an order,
and the match is made by one value: the Beacon's **session id**, sent as
`order.cart_token` on every API call.

`loadBeacon()` in `public/app.js` injects
`https://beacon.riskified.com?shop=<shop domain>` and listens for the
`rskx_ready` event, taking `event.detail.sessionId`. Three deviations from the
copy-paste snippet in the integration guide, all deliberate:

- **The shop domain comes from `/config`**, not from a literal in the markup, so
  it can't drift from the `X-RISKIFIED-SHOP-DOMAIN` header the proxy signs with.
- **It loads immediately** rather than on `window.onload`. The guide defers so
  the Beacon never delays a page; here the page is already up by the time init
  runs, so deferring would only widen the window in which an order could be
  placed before a session id exists.
- **No hidden form field.** Nothing posts a form — the session id goes straight
  into the JSON payload as `cart_token`, and the server signs and forwards it.

The `rskx_ready` listener is attached *before* the script is inserted. The event
fires once and is guarded by a flag, so a listener added afterwards never hears
it.

`cartToken()` falls back to `FIXED.cartToken` when the Beacon hasn't reported
yet, failed to load, or is switched off — the payload is always well-formed. The
env pill in the console shows which is in play, and the call log records the
session id when it arrives. Under `SIMULATE=true` the Beacon is skipped
entirely, since it reports to Riskified and the simulator's whole point is that
nothing leaves the machine.

To debug it, `enableRiskxDebug()` in the browser console prints the Beacon's
state on every load; `disableRiskxDebug()` turns it off.

## The flow

1. **Add funds** → `POST https://sandbox.riskified.com/api/decide`, signed, with
   headers `api-version: 2`, `X-RISKIFIED-SHOP-DOMAIN: otp-recover.demo` and
   `X-RISKIFIED-HMAC-SHA256`.
2. A recoverable decline comes back as `status: "declined"` **with**
   `{"type": "otp", "recommended": true}` in `order.advice.recommendations`.
   The decline is not the answer yet, and there is no token in this response.
3. The page generates a `challenge_access_token` — a UUID, minimum 32
   characters — and posts `POST /recover/v1/otp/initiate` on
   `https://otp-sandbox.self-veri.com`. That call sends the SMS and returns
   `{"widget_token": "<JWT>"}`. Note the snake_case: Riskified's own OpenAPI
   example shows `widgetToken`, but the live API returns `widget_token`. The
   JWT carries the order id and expires 20 minutes after issue, which is also
   the widget's session limit.
4. The page loads `https://otp-sandbox.self-veri.com/otp-widget-sdk.js` and
   calls `window.Riskified.renderOTPWidget(widgetToken, onSuccess, onTimeout)`.
5. The widget runs in an iframe and posts back the same `challengeAccessToken`
   on success, or fires the timeout callback if the customer runs out of time.
6. On success the page sends a **second** `/decide` carrying that token, and the
   verdict from that call is the final answer.

The OTP host is not the decide host, and it versions itself differently: it
wants `Accept: application/vnd.riskified.com; version=2` where `/decide` wants
`api-version: 2`. Both are signed identically.

The challenge access token is generated by **us**, not by Riskified. It goes out
with `/otp/initiate` and comes back from the widget, and comparing the two is
what stops a passed OTP being paired with a different order.

## Triggering a recoverable order

Two sandbox services have to agree, and they key off different words:

- **The decision rules** decide approve or decline. They only decline on their
  own keywords: `decline`, `considerable` or `highrisk`.
- **The eligibility service** attaches the OTP recommendation. It keys off
  `otp` in `order.email` or `billing_address.first_name`.

An order carrying only `otp` comes back **approved** with a recommendation on
it — and an approved order has nothing to recover. Both words must be in the
same payload.

Ticking **Trigger an OTP challenge** uses the split-fields recipe: first name
`otpMichael`, last name `considerable`, written to both `billing_address` and
`customer` so the payload stays internally consistent. This leaves the email you
typed alone, which matters because the demo's story is that the email came from
the checkout form.

The single-field alternative is the email `decline.otp@test.com` — `decline`
satisfies the decision rules and standalone `otp` satisfies eligibility. Swap
recipes in `FIXED.otpTrigger` at the top of `public/app.js`; `considerable` and
`highrisk` decline at different severities.

## Payment methods

The toggle switches `payment_details` between `FIXED.achPaymentDetails` and
`FIXED.cardPaymentDetails`. Along with it switch `gateway` (`plaid_ach` /
`stripe_link`), `line_items[].product_id` (`ach_deposit` / `card_deposit`) and
`line_items[].title`, which is read from `FIXED.lineItemTitle` so the product
name on the page and the title in the payload can't drift apart.

The two payment blocks aren't the same shape. ACH carries `type: 'bank'`, a full
account number and a processor token; card carries no `type`, and
`credit_card_number` is the last four digits only, not a masked full number.

One field is card-only: `submission_reason: 'non_guarantee_decision'`. It sits
at order level in the card payload we were given, and the ACH payload we were
given doesn't have it. It doesn't look payment-specific, so the ACH path may
want it too — but that wasn't confirmed, so it's card-only until someone checks.

## What comes from the page vs what's fixed

Sourced from the checkout: amount (`total_price` and `line_items[].price`),
email (order and customer), the phone number — a searchable dialling-code picker
plus the digits you type, written to **both** phone fields so whichever one the
OTP service reads gets the same value — the OTP first-name flag,
`client_details` from the live browser, and `created_at` / `delivered_at` as real
timestamps. Order `id` is a fresh `crypto.randomUUID()` per attempt, with `name`
mirroring it, so repeat runs never collide. `cart_token` is the Beacon session
id — see above.

Everything else is fixed in the `FIXED` object at the top of `public/app.js` —
addresses, customer profile, KYC block, notes, ACH account details, browser IP,
cart token.

## Known gap

`attachChallengeToken()` in `public/app.js` puts the challenge access token at
`order.challenge_access_token` on the second `/decide`. The field name is now
confirmed — `/otp/initiate` uses exactly that name — but **its placement on the
decide payload is still a guess**. It's isolated in one function; change it
there.

The docs describe `/otp/initiate` but no matching verify endpoint, so the second
`/decide` is this demo's way of closing the loop. That's an inference too.

If you need to check a Riskified field, the docs are more reachable than they
look: `https://developers.riskified.com/llms.txt` indexes every page, and
appending `.md` to a page URL returns its markdown, OpenAPI definitions
included.

## Files

| File | What's in it |
|---|---|
| `config.js` | Endpoint paths, base URLs, credentials, SDK URL. |
| `server.js` | Signing, proxying, webhook verification, SSE, simulator. |
| `public/app.js` | Payload building, decide calls, OTP handling. |
| `public/index.html` | Storefront, console, OTP modal. |
| `public/styles.css` | Brand styling. |

Two details worth knowing before you change the markup: the OTP container must
keep `id="otp-widget"` because the SDK looks it up by that exact id, and it needs
an explicit height — the injected iframe is `height:100%`, so a container with no
height renders a widget zero pixels tall.

## Verification status

The simulator path, HMAC signing, the proxy and the OTP branching are all tested.
`/decide` has run against the live sandbox and returns a well-formed decline,
so the signing and headers are proven against the real host.

**Not yet exercised live:** `/otp/initiate` against the real OTP host, the
hosted widget with a real JWT, and the second `/decide`. Those follow the
published OpenAPI contract and were verified against a local echo server —
correct path, `Accept` header and signature — and the simulator. The call log
shows the full request and response for whatever comes back.
